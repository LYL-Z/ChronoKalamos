# 阶段 3 身份流程

## 游客身份

浏览器调用 Supabase 匿名登录。Supabase 创建真实的 `auth.users` 记录。数据库触发器在 `private` schema 中创建同 UUID 的 `profiles` 记录。浏览器只使用 publishable key，数据访问由 RLS 和显式表权限共同约束。

游客不是可恢复账户。退出登录、清除浏览器数据或更换设备后，旧凭证无法恢复。界面必须在建立游客身份前展示这项风险。

## 邮箱升级

匿名用户通过 `updateUser({ email, password })` 绑定邮箱。该操作保留原用户 UUID，因此已有 `owner_id` 不需要迁移。当前测试项目和生产配置都保持邮箱确认开启。升级的完整产品路径是：

1. 用户提交邮箱和密码。
2. Supabase 发送确认邮件。
3. 用户点击邮件链接。
4. 应用恢复同一 UUID 的正式会话，并读取原存档。

本轮真实测试覆盖了第 1 步以及关闭确认后的数据连续性：UUID 不变，退出后可用邮箱密码登录，存档仍可读。邮件发送、重定向和点击确认尚未由受控收件箱验收，不能把这部分描述为已完成。

如果邮箱已经属于另一个账户，应用不得自动合并两个用户。自动合并会造成账户接管和跨用户数据误归属风险。该情形应要求用户登录已有账户，并使用后续可审计的迁移流程。

## 邮箱登录入口

首页身份面板现在显示真实 Supabase Auth 状态，不再只有游客按钮。未登录用户可以切换两种明确路径：

- `验证链接`：调用 `signInWithOtp`，适合首次登录或忘记密码的用户。
- `密码登录`：调用 `signInWithPassword`，只接受已经设置密码的 Supabase 账户。

密码不会写入本地存储，也不会进入客户端日志。链接或密码登录成功后，面板显示正式账户状态并读取当前用户存档。

Sites 的访问策略仍独立于 Supabase。当前生产站已设为 `public`，因此全球访客可以直接看到邮箱入口，无需先通过 ChatGPT 访问闸门。公开访客复核覆盖验证链接模式、密码模式和 390px 移动断点；复核过程没有提交邮箱或触发邮件发送。

## TOTP 二次验证

TOTP 只向已确认邮箱的正式账户开放。游客不需要配置因子。用户可以注册一个主验证器
和一个备用验证器。注册成功后，Supabase 会使其他会话失效，并把当前会话提升到
`aal2`。

数据库采用 opt-in MFA：没有已验证因子的账户仍可使用 `aal1`；一旦账户存在已验证
因子，存档、回合、检查点和私有上传只接受 `aal2` JWT。三个 owner-scoped
`SECURITY DEFINER` RPC 也执行相同检查，不能绕过 RLS。

Supabase TOTP 不提供恢复码。建议把备用因子保存在另一台受控设备。若两个因子都丢失，
邮箱登录只能恢复到 `aal1`，受保护数据继续被拒绝。管理员必须在核验账户归属后重置
因子。详细流程见 [`docs/totp-mfa.md`](./totp-mfa.md)。

## 未启用入口

短信、手机号登录、Passkey、微信和 QQ 均不显示可提交入口。原有 Twilio 与 Turnstile
代码仅作为关闭的研究准备层保留。`PHONE_AUTH_ENABLED=false` 和
`PHONE_AUTH_PROVIDER=mock` 是默认值。
