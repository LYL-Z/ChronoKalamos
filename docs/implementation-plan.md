## 当前交付边界

阶段 3 已接入 Supabase 匿名身份、邮箱升级、可见的验证链接与密码登录、幂等存档、RLS 和私有上传。生产环境只读取 publishable key。真实邮件投递与点击确认已验收。AI、真实历史地图数据、支付、微信、QQ 和短信登录仍未接入。

阶段 4 已建立 `tang-changan-742` 内容包。当前发布基线为 12 条来源、13 条主张、3 种出身、8 条出身—来源关系、7 条出身—主张关系和 5 个地图证据特征。首页优先读取 Supabase 已发布镜像；本地 JSON 只作为数据库不可用时的显式校验回退。事实主张必须关联来源；合理重建必须说明证据链；叙事虚构不得冒充史实。CHGIS、CBDB 等受限资料仅作研究线索，未复制进商业数据库。地图坐标为明确标注的示意坐标，不宣称为 WGS84 考证复原。

## 实测证据

`npm run test:supabase:live` 使用 `.env.test` 中的两个 publishable 配置执行了真实请求。测试验证了：

1. 两个匿名用户都能建立自己的 `profiles` 和 `game_sessions`。
2. 重复 `client_session_id` 不会覆盖第一次存档。
3. 用户 B 无法读取、更新或删除用户 A 的存档和上传元数据。
4. 用户 B 无法下载或写入用户 A 的私有对象路径。
5. 用户 A 能读取自己的对象。
6. 在受控的“邮箱确认暂时关闭”测试窗口中，游客升级后保留原用户 UUID，并在重新用邮箱密码登录后仍能读取原存档。
7. 匿名客户端可读取 12 条已发布来源、13 条已发布主张和 5 个 742 年有效地图特征；草稿内容不可见，匿名客户端不能写入历史内容表。
8. 匿名客户端可读取 3 种已发布出身及其 8 条来源关系、7 条主张关系；关系表与主表 ID 不一致时，前端拒绝将内容标记为数据库同步。

升级连续性测试在测试项目中临时关闭邮箱确认，测试结束后已恢复开启。因此该证据不等同于“邮件已投递并完成点击确认”。默认 live 测试只验证双用户隔离；提供受控的 `SUPABASE_TEST_UPGRADE_EMAIL` 后才会发起邮箱升级。正式邮箱升级仍要求可用的邮件发送配置和真实收件箱验收。

生产站版本 9 已在 Chrome 登录态下复核。390px 与 768px 均无横向溢出，游客会话和存档刷新后仍可恢复。复核中发现的 5 个小于 24px 的按钮目标已修复。截图与审计记录位于 `audit/phase3-production/`。
